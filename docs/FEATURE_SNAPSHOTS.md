# Feature builds и site snapshots

## Граница репозиториев

Репозиторий сайта выпускает только общий frontend core и независимые фичи. Репозиторий Website Engine владеет админкой, базовым публичным runtime, маршрутизацией, композицией страниц и системными состояниями ошибок. Загруженный feature-код не выполняется как серверный код и не компилируется движком: клиент скачивает его изолированный ESM chunk по digest.

Одна feature не импортирует другую. Фичи могут импортировать core SDK, UI и токены. В ZIP-архиве фичи находятся `manifest.json`, ESM entry-модуль, стили и ресурсы. Импорт проверяет ZIP-пути, manifest, поддерживаемый Engine API и digest. Версия `key@version` неизменяема; повторная загрузка той же версии допустима только с тем же digest.

## Manifest

Manifest редактирует разработчик в исходниках фичи. Админка не предоставляет редактор схемы: она строит обычные поля формы по JSON Schema Draft 2020-12. Например:

```json
{
  "formatVersion": 1,
  "key": "catalog-detail",
  "name": "Карточка товара",
  "version": "1.2.0",
  "engineApi": "1",
  "entry": "entry.js",
  "slots": ["main"],
  "arguments": {
    "type": "object",
    "properties": { "slug": { "type": "string", "title": "Адрес товара" } },
    "required": ["slug"],
    "additionalProperties": false
  },
  "content": {
    "mode": "single",
    "schema": {
      "$schema": "https://json-schema.org/draft/2020-12/schema",
      "type": "object",
      "properties": { "title": { "type": "string", "title": "Название" } },
      "required": ["title"],
      "additionalProperties": false
    }
  }
}
```

JSON Schema задаёт типы и правила проверки. `title`, `description`, `format: "media"`, enum и `x-ui` помогают интерфейсу выбрать подписи и редакторы. Поддерживаемые режимы содержимого: `single`, `collection`, `form`.

### Медиа-поля и ABI 2

Для ABI 2 профили подготовки задаются непосредственно на поле `format: "media"` через `x-media`. Значение контента по-прежнему содержит ID оригинала; движок хранит производные отдельно и при выдаче runtime возвращает объект с `originalUrl`, `src`, `srcSet` и именованными `variants`. Для видео runtime возвращает H.264 MP4 и WebP poster. Сборки ABI 1 продолжают получать старый формат и могут пользоваться сохранёнными общими вариантами.

Media-поля допустимы и в `arguments` фичи. Такие значения привязываются к конкретному placement как постоянный ID медиаобъекта; источник `path` или `query` для media запрещён, чтобы движок мог проверить файл и дождаться обязательных вариантов перед публикацией снапшота. Например, `background.imageSrc` хранится на размещении, поэтому домашняя и каталоговая страницы используют разные фоны.

Общие дизайн-токены и WOFF2-шрифты принадлежат движку. Новые feature archives оставляют в `core.css` только общие правила и semantic bindings, без `:root` значений и шрифтовых бинарников. Runtime получает stylesheet темы и брендовые ресурсы вместе с композицией; снапшот фиксирует ревизию темы, токены, файлы шрифтов и ID логотипа. Старые снапшоты без поля темы сохраняют совместимость со своими общими стилями.

```json
{
  "type": "string",
  "format": "media",
  "title": "Фото карточки",
  "x-media": {
    "accept": "raster-image",
    "renditions": [
      { "name": "card", "width": 900, "height": 680, "fit": "cover" },
      { "name": "preview", "width": 480, "height": 360, "fit": "contain" }
    ]
  }
}
```

`accept` принимает `image`, `raster-image`, `video` или `file`. Варианты используют `contain` или `cover`, максимальные ширину и высоту от 1 до 8192 пикселей. Обработка выполняется фоновой очередью PostgreSQL; публикация не завершается, пока обязательные производные не готовы. GIF, SVG и анимированный WebP остаются оригиналами. Профиль входит в digest; смена настроек не перезаписывает результаты старых снапшотов.

## Визуальная композиция

В `/admin/site` staff-пользователь загружает feature ZIP и визуально редактирует:

- страницы типа обычной страницы, списка коллекции или detail-страницы;
- regex-маршруты и их приоритет;
- упорядоченные placements в слотах, поддерживаемых манифестом;
- аргументы placements как постоянные значения или bindings на именованные capture-группы маршрута;
- источник коллекции и поле поиска для detail-feature, а также ссылку списка на detail-маршрут.

Конфигурация хранится движком как внутренние структурированные данные. В интерфейсе администратора нет текстового поля JSON; исключение — явное действие импорта JSON для контента. Маршруты используют PCRE-подобные выражения с именованными capture-группами, например `^/catalog/(?<slug>[^/]+)$`. Выражение проверяется при сохранении/публикации, имеет лимит длины 500 символов и timeout сопоставления 25 мс. Список маршрутов определяет приоритет.

Аргумент feature объявляется схемой манифеста. Администратор выбирает источник для каждого аргумента: literal либо именованная capture-группа. Runtime приводит строку capture к числу или boolean согласно схеме, затем повторно валидирует итоговые аргументы.

Для каталога list-feature владеет коллекцией. Отдельная detail-feature получает аргумент из URL и выбирает запись через связь с коллекцией и полем. При публикации движок проверяет, что поле существует, содержит скалярные значения и однозначно определяет запись. Отсутствующая запись возвращает 404.

## Контентные режимы

### Single

У фичи один общий набор опубликованного контента. Все её placements читают одну версию, зафиксированную в снапшоте.

### Collection

Фича хранит отдельные записи с ручным порядком. В снапшот входят идентификаторы и версии записей, их содержимое и `sort_order`. Публичный runtime запрашивает записи через серверный фильтр поля и постраничную выборку; браузеру не нужно загружать коллекцию целиком.

### Form

Поля формы задаёт схема манифеста. Публичная отправка использует схему feature build в активном снапшоте. Заявки, статусы и история не включаются в снапшот и сохраняются при обновлении или откате.

Для заполнения контента кнопка **Import from JSON** принимает объект для текущей записи или массив для создания нескольких черновиков. Сначала проверяется весь файл, затем создаются записи; импорт не публикует данные.

## Публикация снапшотов

Черновик конфигурации можно сохранять и редактировать независимо от опубликованной среды. Публикация в dev выполняется транзакцией и создаёт неизменяемый `SiteSnapshot`, содержащий:

- полную конфигурацию base, страницы, маршруты и bindings;
- точные версии и digest всех размещённых feature builds;
- опубликованные версии single и collection записей, включая порядок;
- digest всего перечисленного.

Продвижение переключает prod на тот же `snapshot_id`, не пересобирая контент. Откат dev или prod выбирает предыдущий снапшот. Заявки форм остаются отдельными данными.

## HTTP-контракт runtime

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| GET | `/api/v2/runtime?path=/catalog` | Композиция маршрута и страницы для активного снапшота среды |
| GET | `/api/v2/content/{key}/records?field=&value=&offset=&limit=` | Фильтрованная и постраничная коллекция |
| POST | `/api/v2/forms/{key}/submissions` | Проверка и сохранение заявки по схеме активного снапшота |
| GET | `/feature-assets/{digest}/{asset}` | Неизменяемый feature chunk или asset |

`GET /api/v2/runtime` возвращает route captures, страницы, placements, разрешённые аргументы, опубликованный single/detail content, endpoint коллекции и URL стилей/entry chunks. Публичный runtime загружает только placements совпавшего маршрута. Отсутствующий маршрут или detail-запись даёт 404; отсутствие активного снапшота — 503.

Новый runtime не обращается к структуре legacy JSON напрямую. Старые nginx-сборки можно держать отдельным deployment на время staging и откатывать переключением трафика.

## Admin API

Базовый префикс административных методов — `/api/v2/admin`.

| Метод | Маршрут | Доступ | Назначение |
| --- | --- | --- | --- |
| GET | `/feature-builds` | user | Каталог feature builds |
| POST | `/feature-builds` | staff | Импорт готового ZIP (`application/zip`) |
| GET/PUT | `/site/draft` | user / staff | Чтение и optimistic save визуальной конфигурации |
| GET | `/site/snapshots` | user | История и текущие указатели dev/prod |
| POST | `/site/snapshots` | staff | Создать снапшот и активировать его в dev |
| POST | `/site/snapshots/{id}/promote` | admin | Продвинуть тот же снапшот в prod |
| POST | `/site/snapshots/{id}/rollback` | admin | Активировать снапшот в dev или prod |

`PUT /site/draft` передаёт revision. При конкурентном обновлении сервер отвечает 409. Пользователь работает через графические формы; эти API payloads не требуют ручного редактирования JSON.

## CI и миграция

В репозитории сайта команда `npm run build` проверяет core/features и создаёт `dist/feature-builds/<key>-<version>.zip`. Workflow проверяет lint/typecheck/build, а по тегам `features_v*` публикует отдельные ZIP-архивы.

Одноразовый `scripts/migrate-legacy-site.mjs` переносит сборки, legacy assets, данные, страницы и дерево маршрутов в движок и публикует начальный dev-снапшот. Скрипт также загружает WOFF2-подмножества Alumni Sans SC и общий логотип, закрепляет их за дизайн-системой, а `home.background.imageSrc` и `catalog.background.imageSrc` преобразует в media-аргументы отдельных размещений. Пример вызова и порядок проверки приведены в корневом [README](../README.md). После сверки dev администратор продвигает тот же снапшот в prod. На staging старый nginx deployment сохраняют отдельно как путь быстрого возврата трафика.
