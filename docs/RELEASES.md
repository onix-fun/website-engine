# Релизы сайта, среды и HTTPS

В этом документе описан конвейер выката сайта: неизменяемые zip-артефакты,
две среды (dev/prod), аудит событий, источники релизов (Git-провайдеры) и
TLS/ACME-роутинг по доменам.

## Основные понятия

- **Релиз** (`site_releases`) — неизменяемый zip-артефакт (sha256, размер,
  манифест с перечнем файлов). Распаковывается один раз при импорте, дальше
  среда сервера только читает готовую директорию, поэтому активация мгновенная.
- **Среда** (`site_environments`) — `dev` и `prod`. У каждой среды свои:
  имя, публичный base URL, домены, CORS-origins, флаг TLS и ревизия
  (optimistic concurrency для PATCH).
- **Активация** — «среда указывает на релиз». Один релиз можно активировать
  в dev и в prod одновременно (продвигать артефакт по средам).
- **События** (`release_events`) — журнал `import`/`activate`/`rollback`
  с актёром и метаданными. При активации в метаданные записывается снимок
  `release_version` + `feature_versions` (состояние схем на момент выката).

## Импорт релиза

### Ручная загрузка

`POST /api/v1/admin/releases` (multipart: `artifact`, `version`, `tag`).
Архив обязан:

- быть корректным zip с `index.html` в корне;
- не содержать записей с `..` и symlink-ами;
- укладываться в лимиты `MAX_RELEASE_BYTES`.

Ответ — JSON релиза с `artifact_sha256` и манифестом. Некорректные архивы
отклоняются кодом 400 с пояснением.

### Импорт из источника (GitHub / GitLab / Gitea)

1. В разделе «Сайт» нажмите «Добавить источник»: выберите провайдера,
   укажите URL репозитория (например `https://github.com/owner/repo`),
   regex-шаблон имени артефакта (например `dist-.+\.zip`) и, при
   необходимости, персональный токен. Токен шифруется AES-GCM ключом
   `RELEASE_MASTER_KEY` и никогда не возвращается в API.
2. «Релизы источника» — список релизов репозитория (теги + активы).
3. «Импортировать» — актив скачивается провайдером на сервер, проходит ту же
   валидацию, что и zip-загрузка, и появляется в списке релизов.

`POST /api/v1/admin/release-sources/{id}/sync` принимает `asset_url`,
`version` и `tag`; если `version` не указан, используется первые 12 символов
sha256 артефакта.

## Активация, откат и продвижение

`POST /api/v1/admin/releases/{id}/activate` — переключение указателя среды.
Права: dev — админ/модератор, prod — только админ.
`POST /api/v1/admin/releases/{id}/rollback` — откат на предыдущий релиз
(в UI кнопка автоматически выбирает предыдущий по списку).

## Настройки сред

Раздел «Сайт» → карточка среды → «Настроить среду» (или страница
`/releases/environments/{dev|prod}`, права: только админ):

| Параметр           | Описание                                                          |
| ------------------ | ----------------------------------------------------------------- |
| Название           | Отображаемое имя среды                                            |
| Public base URL    | Используется в absolute-ссылках; БД приоритетнее ENV-конфига      |
| Домены TLS/SNI     | Домены этой среды; не должны пересекаться между dev и prod        |
| CORS origins       | Применяются без перезапуска (кеш сбрасывается при изменении)      |
| HTTPS/ACME toggle  | Включение TLS для среды                                           |

PATCH `/api/v1/admin/site/environments/{key}` требует актуальную ревизию
(409 + текущая ревизия при конфликте). Обновляются только переданные поля.

## CORS

Публичное API каждой среды и раздача контента обслуживаются
`DynamicCORS`: пока список CORS-origins в БД пуст, работают bootstrap-origins
из конфигурации (`PUBLIC_CORS_ORIGINS[_DEV|_PROD]`). Как только оператор
заполнил список в админке — работает только он.

## HTTPS / ACME / SNI

При `TLS_ENABLED=true` сервер поднимает два listener'а:

- `HTTPS_ADDR` (по умолчанию `:443`) — HTTPS с autocert (Let's Encrypt;
  `ACME_STAGING=true` — staging-CA), для каждого домена двух сред.
- `TLS_HTTP_ADDR` (`:80`) — ACME HTTP-challenges и редирект на HTTPS.

Роутер сопоставляет запрошенный хост со средой (через
`site_environments.domains`, обновляемые раз в минуту) и раздаёт контент
соответствующей среды. Запросы по сертификатам от чужих хостов получают
421 Misdirected Request.

## Инварианты контента при выкатах

- `prod` не может опережать `dev` — DB-триггеры следят за порядком версий.
- Нельзя снять запись с публикации в dev, пока она опубликована в prod;
  правильный порядок — сначала `unpublish` в prod, затем в dev.
- Публикация строгой схемы проверяет активный контент dev: несовместимые
  записи блокируют publish (422 с перечнем проблемных полей).

## Переменные окружения

| Переменная               | Назначение                                        |
| ------------------------ | ------------------------------------------------- |
| `RELEASE_MASTER_KEY`     | 32-байтный ключ шифрования токенов источников     |
| `MAX_RELEASE_BYTES`      | Максимальный размер артефакта (байт)              |
| `RELEASE_CACHE_DIR`      | Каталог кеша распакованных релизов                |
| `TLS_ENABLED`            | Вкл/выкл HTTPS-listener и autocert                |
| `HTTPS_ADDR`             | Адрес TLS-листенера (`:443`)                      |
| `TLS_HTTP_ADDR`          | Адрес challenge-листенера (`:80`)                 |
| `ACME_EMAIL`             | Аккаунт Let's Encrypt                             |
| `ACME_STAGING`           | Staging-CA для тестов                             |
| `TLS_CACHE_DIR`          | Каталог хранения сертификатов                     |
| `PUBLIC_CORS_ORIGINS_*`  | Bootstrap CORS-origins по средам                  |

Compose: при `TLS_ENABLED=true` откройте в server-сервисе порты
`443:443` и `80:80` (в `compose.yaml` для этого раскомментируйте
соответствующие строки в разделе ports).
